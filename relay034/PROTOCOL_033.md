# Snowyard Relay 0.3.3 — Roster Protocol v2 (Java-клиент следующего этапа)

**Статус: серверная реализация, интеграция Java ещё не выполнена.** Старые `rosterVersion=0` и `1` сохранены в целях совместимости; исправленная логика включается только через `rosterVersion:2` в `hello`.

## Подключение

```json
{"type":"hello","version":1,"nickname":"Test","mode":"brawl","room":"global","rosterVersion":2}
```

Клиенты v1 и v2 не смешиваются в одной комнате. Brawl продолжает использовать snapshot_manifest / snapshot_get / sync_poll / sync_finish.

## Вступление (не больше одного нового участника на транзакцию)

1. Подключающийся получает снимок и воспроизводит историю, но **не получает право голосовать как ACTIVE**.
2. По окончании `sync_finish` Relay добавляет его в очередь. Если уже идёт проверка, она не перезапускается; следующий участник ждёт.
3. Relay останавливает комнату и отправляет **только уже активным** `roster_prepare`, содержащий `generation`, `players` активного состава и — если существует ранее подтверждённая контрольная точка — `tick`/`hash`.
4. Активные клиенты останавливаются, при наличии заданной контрольной точки выравниваются по ней (при необходимости — через сохранение и replay), после чего каждый посылает `roster_ready` с одинаковыми `generation`, `tick` и SHA-256 state hash.
5. Если все ACTIVE согласны, Relay посылает **только назначенному вступающему** `roster_checkpoint` (`generation`, `tick`, `hash`). Вступающий должен доказать, что полностью воспроизвёл состояние до указанного тика и полученный хеш совпадает.
6. Вступающий отвечает `roster_join_ready`. Только после точного совпадения Relay рассылает `roster_commit`, устанавливая состав на `tick+1`.
7. Другие ожидающие клиенты рассматриваются в следующих транзакциях; P3 не сбрасывает голосование P1/P2.

Пример подтверждения вступающего:

```json
{"type":"roster_join_ready","generation":7,"tick":1200,"hash":"<64 hex digits>"}
```

Учитывайте: `roster_prepare.tick` может отсутствовать или быть 0, если контрольной точки ещё нет. В этом случае активные участники должны сами согласовать реальное одинаковое состояние; сервер не изобретает тик. Если значения расходятся, сервер не продолжает игру автоматически.

## Выход

Выход ACTIVE создаёт новую транзакцию состава даже без вступающих участников. Оставшиеся подтверждают новый общий тик/хеш; сервер рассылает `roster_commit`. Выход ожидающего вступления не меняет ранее согласованный ACTIVE состав. При отключении во время транзакции она прерывается и создаётся заново, если состав изменился.

## Тайм-аут

Через 20 секунд без завершения транзакции Relay рассылает `roster_aborted`. Непрошедшим вступающим требуется новая загрузка/проверка; сервер не подделывает голосов. При незавершённом выходе ACTIVE игра остаётся на паузе: нельзя разрешить команды со старым составом.

## Расхождения мира

Повторное расхождение хешей включает `recoveryRequired`. Для протокола v2 один `coordinator_resume` больше не снимает такую паузу.

Когда существует корректный снимок, каждый активный участник может подтвердить его восстановление:

```json
{"type":"recovery_ready","tick":1200,"hash":"<64 hex digits>","snapshotId":3}
```

Все активные участники должны подтвердить одинаковый ожидаемый `tick`, `hash` и текущую версию снимка. Только тогда Relay рассылает `session_resumed`. Если большинство не определилось или снимок не существует, **автоматического восстановления пока нет**: потребуется дополнение сервера и клиента. Relay не способен доказать правильность физического состояния по одним SHA-256 отпечаткам; это подтверждение участников, а не криптографическая аттестация физики.

## Обязательные ограничения следующей Java-версии

- Нельзя отправлять `roster_ready` как только закончена загрузка: оно разрешено только ACTIVE из `roster_prepare`.
- `roster_join_ready` отправляется только назначенным ожидающим участником после проверки checkpoint.
- Поддержать `roster_checkpoint`, `roster_aborted`, `recovery_ready`.
- При получении целевого `roster_prepare.tick` нельзя просто объявить собственный текущий тик подтверждённым; требуется сохранённая история/откат/догон по нему.
- При ошибке/тайм-ауте не выходить молча домой, а показывать причину и позволять повторную загрузку.
- `rosterVersion=1` не пользуется новыми гарантиями.

## Известные пробелы

- Полностью автоматический resync при неизвестном или конфликтном state hash ещё не реализован.
- Серверный выбор большинства не доказывает корректность симуляции.
- Snapshot SHA-256 доказывает целостность байтов, но не авторитетность заявленного тика; строгая привязка snapshot к checkpoint пока не выполнена.
- Текущий all-player lockstep, расход O(N²) доставок, блокирующая локальная запись снимка и batch-by-count остаются задачами будущих релизов.
- Новый протокол не проходил end-to-end тест на Render с Java-клиентом.
